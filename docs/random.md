# Kernel randomness

`getrandom`, `/dev/random`, `/dev/urandom`, and ELF `AT_RANDOM` consume one kernel generator. A BLAKE2s-256 pool mixes inputs and derives keys. ChaCha20 generates each 64-byte block with counter and nonce zero: the first 32 bytes replace the old key, and up to 32 bytes from the second half are returned. The unused tail and temporary block/state are erased. Each following block uses the new key, so there is no repeated key/counter pair. Pool extraction also advances its state before retaining it. The current single-CPU kernel serializes these operations with interrupts disabled; adding SMP requires synchronization at this module.

Boot checks CPUID leaf 7, subleaf 0, EBX bit 18 before executing RDSEED. CPU entropy is trusted by default; `random.trust_cpu=off` disables that source. Four successful 64-bit words establish the 256-bit initialization threshold. Each word gets at most ten instruction attempts, and a clear carry flag discards the candidate. Zero, all-ones, duplicate words within a sample, and repetition of the previous sample's final word reject the whole candidate. Failed candidates are erased and retried after 100 ms. A successful initialized source is sampled again after 60 seconds. Failed reseeding preserves the existing generator and retries; it never substitutes a constant seed or an unchecked instruction result. RDRAND alone does not initialize this implementation.

These checks catch some failed or stuck sources; they do not establish or certify physical entropy quality. Crediting RDSEED depends on the CPU or hypervisor implementation and the selected trust policy. Boot counter values and ordinary writes to either device are mixed without credit. If RDSEED is unavailable, fails, or is disabled by policy, initialized output remains unavailable until a supported trusted source succeeds or an administrator explicitly credits input.

Modern and legacy virtio RNG devices use queue zero with writable buffers. A sample must supply 32 bytes within one two-second deadline, including every short completion. Descriptor ownership, completion lengths, device status and sample health are checked. Invalid or timed-out devices are reset; resources are released only after the reset is acknowledged. Healthy samples pass through the same word validation as CPU input. `random.trust_virtio=on` explicitly permits initialization and reseeding from the hypervisor source. The default policy mixes validated virtio input without credit. Healthy sources refresh after the real 60-second interval. Readiness queries and random reads also service pending input so a runnable userspace process does not prevent completion progress.

## Linux interface behavior

`getrandom` accepts `GRND_NONBLOCK` (1), `GRND_RANDOM` (2), and `GRND_INSECURE` (4). Unknown bits and the combination of `GRND_RANDOM` with `GRND_INSECURE` return `EINVAL`. Flags have Linux's unsigned-int width. Default and `GRND_RANDOM` requests wait for initialization; `GRND_NONBLOCK` returns `EAGAIN` before it. Initialization is checked even for a zero-length request. Explicit `GRND_INSECURE` bypasses that wait and does not establish readiness. Once ready, requests of at most 256 bytes complete without a signal-induced partial result. Larger requests can return a short result of up to 4096 bytes. Invalid destinations return `EFAULT`, or the already-copied count when a later destination chunk fails. Initialization waits are interruptible and honor `SA_RESTART`.

`/dev/random` waits for initialization; `O_NONBLOCK` reads return `EAGAIN` before it. Scalar zero-length device reads also check readiness, after validating the destination address. Empty `readv` requests return zero before device dispatch, matching the Linux VFS contract. Poll reports readable after initialization and writable before initialization. `/dev/urandom` follows Linux's early-output behavior and is readable before initialization; that output has the same limitation as `GRND_INSECURE`. Both devices return up to 256 bytes per read and accept uncredited writes. ELF `AT_RANDOM` uses the same generator, with early uninitialized output permitted so init can bootstrap. Applications requiring initialized output must use default `getrandom` or `getentropy`. The pinned musl `getentropy` implementation retries `EINTR` internally and rejects requests larger than 256 bytes with `EIO`.

`RNDGETENTCNT` reports the monotonic initialization count from zero through 256, including partial credit. The following commands require effective `CAP_SYS_ADMIN`, checked before user pointers: `RNDADDTOENTCNT`, `RNDADDENTROPY`, `RNDZAPENTCNT`, `RNDCLEARPOOL` and `RNDRESEEDCRNG`. Credits saturate at 256; negative counts return `EINVAL`. `RNDADDENTROPY` mixes the copied input but credits it only after the whole requested buffer is imported. A failed partial copy leaves its copied prefix uncredited. A negative signed buffer length follows Linux's size conversion and user-range checks, producing `EFAULT`. Clear and zap are privileged no-ops and preserve initialization, matching the pinned Linux implementation. Explicit reseeding returns `ENODATA` before initialization. Unknown and removed pool commands return `EINVAL`; ioctl command values use Linux's unsigned-int width. Crediting is an administrator's assertion about input quality, rather than a measurement by the generator.

## Persisted seed service

`random-seed boot|load|rotate` uses `/var/lib/axiom64/random` by default; `--directory` selects another absolute path. The service requires root UID/GID, root-owned parent directories without group or other write access, a private 0700 leaf directory, and regular 0600 seed and lock files. It walks paths with directory descriptors and refuses symlinks, unexpected hardlinks, unsafe ownership, oversized or truncated seeds, and unsafe temporary files. A nonblocking exclusive lock allows one service owner at a time.

`load` mixes an existing 32-byte seed through an ordinary device write without credit. Stored, replayed and cloned seeds cannot establish readiness. `boot` and `rotate` first load that input, then obtain 32 initialized bytes through `getrandom`. `--nonblock` reports `EAGAIN` before generating a replacement when the kernel is unready. Rotation writes and synchronizes a private temporary file, synchronizes a previous-generation checkpoint, renames the complete replacement, and synchronizes its directory. A failure before the commit attempts to retain or restore the previous complete seed. A committed replacement can leave a verified checkpoint for the next invocation to recover if cleanup fails. Orphan cleanup is bounded and checks every recognized temporary file before removing it; unrelated files remain intact.

The ordinary images install the static service and an empty private seed directory. Normal init starts a nonblocking boot rotation, reaps its child, and retries failures after at least one second; success completes this startup task. The service never blocks init while waiting for an initialized source. Init formats each seed-supervision record into one bounded write beginning with a newline, so an asynchronous spawn or reap starts its own record during console input echo. The observer still requires the complete PID, status, timestamp and line ending. Both ordinary profiles are covered by the installed-service, fresh-disk, signature and unready-console checks below.

`scripts/random_seed_crash_test.py` interrupts the production rotation logic at eight boundaries around temporary creation, writing, synchronization, checkpoint publication, rename, directory commit and cleanup. The fixture calls the real filesystem operations, then stops its child. Guest cases kill the actual VM with `SIGKILL`, retain the disk, and start a fresh kernel with CPU initialization disabled. The ordinary service recovers through an explicit [checked ext2 mount](ext2.md#supported-format-and-operations). Complete old or published seed bytes survive, orphan temporaries disappear, unrelated files remain intact, and recovery must retain zero initialization credit and `EAGAIN`. Both existing-seed and first-seed cases use independent host disk exports and filesystem checks.

Native process-crash comparisons use actual ext2 mounts and all three libc profiles. They kill the child and unmount before reopening; they do not claim native machine power-loss coverage. Run them in a private mount namespace:

```sh
sudo unshare --mount --propagation private python3 scripts/random_seed_crash_test.py --native
python3 scripts/random_seed_crash_test.py
python3 scripts/random_seed_recovery_test.py
```

The recovery-policy harness retains default dirty-volume rejection, validates read-only and writable checked mounts across four ext2 layouts, and runs all 23 existing malformed/unsupported cases plus error-state and orphan-chain controls under the new option. Rejected disks must remain byte-identical. `scripts/random_seed_fault_test.py` separately injects actual virtio writes and flush failures and exhausts an ext2 volume. These checks cover completed syscall boundaries and deliberate backend errors; interrupted metadata-sector writes still require general filesystem repair work.

## VM memory restoration

On QEMU x86-64, the kernel reads the current hypervisor generation ID from the bounded `fw_cfg` file directory. It validates the named 4096-byte file and reads the 16-byte ID at offset 40 twice, with bounded retries for a restore that interrupts a read. The initial ID and changed IDs are mixed without entropy credit. A detected change immediately rekeys an already initialized generator during the refresh. It cannot initialize an unready generator or increase partial initialization credit. An active generation-read failure withholds readiness; reads that reach the generator return `EIO`. A later valid read can recover.

The hypervisor must provide a new ID when restoring a snapshot into a new generation or cloning a VM. Reusing the ID also reuses saved generator state: same-instance and same-ID controls deliberately demonstrate this limitation. The adapter currently uses QEMU's I/O-port `fw_cfg` interface. It does not establish support for other hypervisors' ACPI generation devices or physical hardware.

An active adapter read failure also fails ELF auxiliary-vector generation with `EIO`; failed exec preserves the previous memory and credentials. `scripts/random_generation_exec_test.py` uses a recorded debugger mutation of the adapter's directory slot to force its bounded read failure. Both musl linkages and firmware modes require sixteen failed execs, unchanged original auxiliary data, a still-active direct random-read error, and successful exec after restoring the slot. This is deliberate adapter fault injection, separate from the real memory-restore matrix.

`make test-random-generation-native` checks discovery bounds, malformed entries, selector changes, interrupted and failed reads, unchanged IDs, immediate rekeying, and zero/partial credit under ASAN/UBSAN. `python3 scripts/random_snapshot_test.py` performs eight cold boots across both musl linkages, BIOS/UEFI, and initialized/unready modes. Each uses an actual qcow2 memory/device checkpoint for a same-instance restore, a new process with the same ID, and a new process with a changed ID: 24 VM processes and 24 memory restores. Snapshots are taken while the guest waits to issue a fresh random request. The initialized unchanged-ID controls reproduce the exact 32-byte sample; changed IDs produce a different first sample without waiting for the periodic source reseed. All unready restores retain zero credit and `EAGAIN`. Restoring memory also restores previously generated userspace keys and buffers; this comparison does not establish their freshness. The harness retains actual disks, image snapshot tables, serial logs, QMP commands/responses, executable hashes and source inputs.

The primitives follow [RFC 8439](https://www.rfc-editor.org/rfc/rfc8439.html) and [RFC 7693](https://www.rfc-editor.org/rfc/rfc7693.html). Instruction semantics follow the [Intel DRNG guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html). Early output, pool writes, fast key erasure, and initialization waits are compared with [Linux v6.12](https://github.com/torvalds/linux/blob/v6.12/drivers/char/random.c); empty read and vector behavior follows the [Linux v6.12 VFS](https://github.com/torvalds/linux/blob/v6.12/fs/read_write.c); libc retry follows [musl v1.2.5](https://git.musl-libc.org/cgit/musl/tree/src/misc/getentropy.c?h=v1.2.5). QEMU 8.2.2 TCG routes RDSEED through its [random instruction helper](https://github.com/qemu/qemu/blob/v8.2.2/target/i386/tcg/int_helper.c), which obtains bytes through `qemu_guest_getrandom`. Generation handling follows the pinned [QEMU generation device](https://github.com/qemu/qemu/blob/v8.2.2/hw/acpi/vmgenid.c) and [fw_cfg migration implementation](https://github.com/qemu/qemu/blob/v8.2.2/hw/nvram/fw_cfg.c). These local checks depend on the documented hypervisor trust and ID policies; they do not estimate physical entropy quality.

Administrative command ordering follows [the pinned Linux random implementation](https://github.com/torvalds/linux/blob/3857c2fe5449541e24afc5efdb0f81a8a8f9a3a0/drivers/char/random.c) and [user-buffer import](https://github.com/torvalds/linux/blob/3857c2fe5449541e24afc5efdb0f81a8a8f9a3a0/lib/iov_iter.c). The device contract follows the [Virtio 1.3 entropy device specification](https://docs.oasis-open.org/virtio/virtio/v1.3/virtio-v1.3.html).
