# Account records and authenticated identities

Axiom64 stores protected user and group records and uses private password entry to authenticate local sessions. Normal startup creates an administrator on a fresh disk, then requires login. Later boots preserve that account and require authentication again. Account tools provide administration, login, elevation and password changes; supervisors manage private terminals, graphical sessions and login records. Complete persistent administration and recovery from storage or process failures remain under development.

## Records and transactions

`userspace/accounts/store.c` validates trusted directory ancestors, root ownership, exact file modes and single-link regular files. A process lock covers one complete immutable passwd/group/shadow generation. A successful update writes and synchronizes all three files before replacing the current pointer. It holds the preceding pointer through publication and cleanup using `O_PATH|O_NOFOLLOW`, verifies its root ownership, single link, namespace identity and exact generation target, and releases it at transaction cleanup. This keeps the replaced symlink's body available during interrupted ext2 retirement. Older-generation cleanup also retains its validated directory descriptor through removal and parent synchronization, preserving the empty inode's body until the namespace is durable. Passwd and group use mode 0644; shadow and the lock use 0600. The current and preceding generations remain after successful cleanup. Missing current state with unexplained generations fails closed.

`database.c` owns the transaction and account/group relationships. `record.c` validates and serializes the seven-field passwd, four-field group and nine-field shadow layouts. Duplicate names or IDs, dangling primary groups or members, repeated shadow records, invalid numbers, malformed fields and inconsistent aging settings are rejected. Names use one to 32 lower-case ASCII letters, digits, underscores and hyphens, starting with a letter or underscore. IDs cover 0 through 4,294,967,294; root is the canonical UID/GID-zero account and group. Each serialized file is bounded to 1 MiB. Record counts and memberships use dynamic storage within that bound.

Renaming a user preserves numeric membership references; serialization emits the new name consistently. Changing a UID updates membership references. Changing a group ID updates primary-group references. A primary group cannot be deleted while a user depends on it. Invalid operations and failed allocation preserve the previous logical database. A commit reports whether publication happened when a later durability or cleanup operation fails, so callers cannot assume rollback after every error.

## Root administration

`accountctl` accepts an explicit command interface for bootstrap, user/group creation, deletion and rename, home/shell record changes, membership changes, password changes and locking. It requires real/effective UID zero and effective GID zero. `--database PATH` selects an isolated store for fixtures or root administration; the normal destination is `/etc/axiom64/accounts`.

Bootstrap creates a locked root account, the administrator's private primary group, and the `sudo` group. It hashes the administrator's password with maintained libxcrypt yescrypt, creates a private mode-0700 home owned by that administrator, and publishes the complete account set once. Later bootstrap attempts fail. `accountctl` reads passwords from a descriptor supplied by a protected pipe or provisioning source. `account-access provision` uses private terminal entry and confirmation. Password values are never command-line arguments.

Home creation prepares a temporary directory in the trusted, root-owned parent, sets ownership and mode, synchronizes it and publishes with `RENAME_NOREPLACE`. The parent cannot be writable by other identities, including a sticky directory. Existing final entries are preserved. A held directory descriptor identifies the created inode through the account commit. If the accounts remain unpublished, cleanup removes only that empty inode; replacements and directory contents are preserved. A late mkdir error or failed open can leave an unproven `.home-*` temporary entry. It is preserved and reported for root review, and never published as the requested final home.

Creation also stores a random 16-byte proof in `trusted.axiom64.home` before changing ownership. The filesystem must support trusted attributes, and the creator needs `CAP_SYS_ADMIN`. Ordinary owners cannot read, list, copy or remove this proof. The generation transaction durably publishes a root-owned mode-0600 `home-intent` before creation. Its checked binary record binds the old and planned generation, home path, UID/GID and creation key. A protected staging file and the planned generation also carry matching trusted attributes. Both command administration and private bootstrap use this store-owned protocol.

Opening the store under its lock recovers a validated pending intent. If the actual current pointer names the planned complete generation, recovery keeps the attested published home. If it still names the preceding generation, recovery removes only attested empty pending/staging homes and the associated owned unpublished generation. A reported rename error does not imply rollback: the store inspects actual pointer visibility before cleanup. UID and inode numbers alone never authorize deletion. Malformed authority, an unexpected current generation, foreign replacements and nonempty homes are preserved. A validated blocked rollback can leave the preceding complete generation readable while every update rejects the recovery error; `accountctl` reports that state. Unproven creation gaps and structural/authority damage require root review. Real storage failure and VM power-loss acceptance remain separate work.

Examples, with descriptor 3 prepared privately by the provisioning caller:

```sh
accountctl bootstrap admin /home/admin /bin/bash --password-fd 3
accountctl group-add developers 1001
accountctl user-add alice 1001 developers /home/alice /bin/bash
accountctl member-add developers admin
accountctl password alice --password-fd 3
accountctl lock alice
accountctl unlock alice
accountctl show alice
```

New homes use trusted root-owned ancestors and reject existing final entries, including symlinks. Pre-publication rollback removes only the newly created empty home; it never recursively deletes its contents. Account deletion preserves home data. The command's status output reports whether a password is set or disabled without disclosing the hash. Wider user/group administration interfaces remain future account work; the authentication aliases are described below.

A device error before creation authority is established can leave an unproven root-owned staging entry. Recovery preserves it and reports the error for root review. Once the protected intent and inode proof exist, a retry can recover an empty unpublished home safely. Nonempty or foreign entries remain intact; complete real-device error acceptance is still required.

Administration holds the database lock, then the logbook lock, through checking and publication. User deletion, renaming, home changes and numeric UID reuse reject live session leases or processes using that UID. Group deletion/renaming and numeric GID reuse check real/effective/saved/filesystem GIDs and supplementary groups, together with relevant live session records. The process check reads actual kernel procfs status for every process and thread, including saved identities and the last of all 65,536 supported supplementary groups. Unavailable procfs, denied inspection, malformed records and non-procfs files fail closed; a task that exits during inspection may disappear normally. These checks extend the [process inspection used by Linux account tools](https://github.com/shadow-maint/shadow/blob/4.18.0/lib/user_busy.c), with explicit failure handling rather than treating a failed scan as unused. First-administrator provisioning also checks its selected numeric identities before creating the home or publishing accounts.

Password locking, password changes, shell updates and membership changes remain available while a user is active. They affect future authentication; existing processes retain their installed credentials. Every accepted operation records its specific event kind, target, intent and completion status without recording command arguments or secret data. `--records PATH` selects an isolated protected logbook for root administration and fixtures.

## Authentication and credential installation

`auth.c` validates the protected database and checks the maintained password verifier, aging fields and optional membership in `sudo` inside one locked snapshot. Wrong passwords, missing or locked accounts, account expiration, expired inactivity and disabled elevation deny access. Password aging follows the documented [shadow fields](https://man7.org/linux/man-pages/man5/shadow.5.html) and the boundary behavior checked against [Linux-PAM 1.7.1](https://github.com/linux-pam/linux-pam/blob/v1.7.1/modules/pam_unix/passverify.c). A forced or expired password change produces a profile that cannot install session credentials until reauthentication after the change. Returned profiles retain identity and group data without retaining the hash.

Installing a nonroot profile sets all real/effective/saved and filesystem UID/GID values, installs supplementary groups, clears retained capabilities, and verifies the resulting credentials. Service mode additionally sets no-new-privileges. Login environment construction replaces inherited variables with the identity's HOME, USER, LOGNAME and SHELL, a fixed PATH and locale, and an optional validated terminal type. A failed credential transition must terminate the child; it must never continue an application after a partial drop.

Real root administrators can select an existing locked service identity without a password. This operation is separate from password authentication. Ordinary session profiles permit later use of explicitly authorized set-ID tools; service profiles prevent privilege acquisition through exec.

## Private input and supervised terminals

`secret.c` reads a bounded password from the caller's foreground controlling terminal. It requires canonical input, disables both echo flags before displaying the prompt, drains invalid or overlong lines, and clears the complete output on failure. Input and prompt output use an [atomic signal-aware wait](https://man7.org/linux/man-pages/man2/select.2.html), so cancellation cannot leave the reader waiting for another keystroke. Success, EOF and cancellation restore the original terminal attributes, descriptor flags, signal actions and signal mask. SIGINT and SIGTERM take their original action after that state is restored. A caller must clear a successful password after verification or hashing.

PTY slaves start locked, with mode 0600 and the creator's filesystem UID/GID. Unlocking and relocking use the actual master lock; denied slave opens report EIO and invalidate existing slave I/O until a successful reopen, matching the [Linux 6.17 PTY implementation](https://github.com/torvalds/linux/blob/v6.17/drivers/tty/pty.c). Closing the final master unlinks the slave and hangs up its controlling session. Retained slave descriptors keep their own inode and ownership; an unrelated pair cannot reuse their identity. Unreferenced RAM device inodes are reclaimed. Terminal operations on unrelated character devices fail with ENOTTY. Session takeover requires the explicit privileged operation, and foreground/session queries enforce controlling-terminal membership.

`session.c` runs a command on a private PTY in a new session. Before exec, the child installs its complete profile, clears inherited environment, sets umask 077 and enters its home. A privileged begin callback runs after that setup and before the command is allowed to execute; failure prevents exec. The supervisor relays terminal input/output and resize events, reaps the child, closes the private master, restores the caller's terminal attributes and flags, and invokes the end callback. An ordinary caller's outer terminal ownership does not change. SIGTERM cleanup records the child's real exit status before restoring the original signal action. SIGKILL closes the sole private master through descriptor teardown; restoring an outer physical terminal and reconciling stale records after that forced failure belong to the remaining init/record integration.

`recorded.c` connects the real session callbacks to the protected journal. Registration takes the database and logbook locks in that order and verifies that the authenticated generation is still current. A changed generation denies the child before exec. Sudo registration also revalidates the actor's explicit membership. Complete job-control behavior and broader process/resource isolation remain subject to their existing feature requirements.

## Authenticated desktop

Normal login starts one graphical seat for the authenticated user, alongside the private serial shell. The trusted Xorg process retains root-only access to the framebuffer and input devices. The window manager, xeyes, xterm and selected shell use the user's ordinary identity, groups, home and environment. The terminal launcher checks its actual slave descriptor and sets mode 0600 before executing the selected shell. The image supplies `/etc/shells` explicitly because imported package installation hooks do not run.

Each seat receives a fresh initialized 128-bit [MIT-MAGIC-COOKIE-1 secret](https://www.x.org/guide/communication/). Xorg reads a root-owned mode-0600 authority file; the user's copy has mode 0400. TCP listening is disabled. Authorized applications share the display's X11 input and output access. Other users cannot read the cookie, open the raw display/input devices or signal the seat processes.

A permanent root-owned file lock owns the seat. Each child waits before exec until the supervisor durably records its PID and birth time; losing the supervisor before release prevents exec. The supervisor observes exited children with `waitid` and `WNOWAIT`, retaining their process identities until it retires their owned groups and reaps them. It revokes authorization files and clears framebuffer pixels when either shell ends or a desktop process fails. Parent-death SIGKILL terminates direct children after supervisor failure; detached descendants still need wider lifecycle controls. `startx` invokes the same authenticated access path.

Recovery validates the complete directory inventory and a canonical, checksummed state record before changing files or pixels. The record binds the boot UUID, each recorded process's start time, and the user's UID/GID. A matching live process, held lock, live display, damaged metadata or unknown artifact blocks recovery. Stale records from another boot or process incarnation never authorize signaling the current occupant of a reused PID. Known stale Xorg locks and sockets require exact ownership, modes and saved server identity; incomplete lock writes fail closed.

The strict graphical acceptance matrix passes ten BIOS/UEFI RAM/ext2 boots across modern and legacy block transports, with fifty authenticated sessions and eight host filesystem checks. Every session verifies actual X11 authorization, pixels, keyboard input and ordinary identity. It retains 110 framebuffer captures, sixty black login screens and 320 retired-process checks. Every boot has a distinct kernel UUID and meets the unchanged 180-second deadline. Integration with every existing desktop/service gate and wider persistent crash recovery remain required.

## Session journals and login records

`logbook.c` owns an exclusive root transaction in a mode-0755 directory. Its journal, lock, failed-login records and text audit log have mode 0600; public utmp/wtmp projections have mode 0644. Every file must be root-owned, regular and single-link. The journal retains full-width timestamps, identities, sequence numbers and random session tokens. Versioned frames use the [CRC-32 polynomial](https://www.rfc-editor.org/rfc/rfc1952) for accidental-corruption detection. Root ownership supplies authorization. A partial final write is repaired only after all complete frames validate; corrupt complete frames and inconsistent session relationships fail closed.

Each supervisor holds a private flock lease created after fork. The command closes inherited descriptors before exec and cannot keep that lease alive. Closing a normal session records its actual wait status. If the supervisor dies, a later transaction can exclusively lock the abandoned lease and append a distinct recovery event without inventing an exit status. Missing or malformed leases fail closed. Terminal reuse is keyed by session token, so a delayed old logout cannot clear a newer occupant.

The classic projections use the Linux x86-64 384-byte utmp wire layout independently of libc's internal declarations. An executed GNU libc client reads the actual guest utmp/wtmp/btmp files through `utmpxname`, `setutxent` and `getutxent`. This depends on the kernel's POSIX record-lock implementation; a host reader does not substitute for that guest path. Its [portable verification kit](../vendor/gnu-utmp-reader/README.md) pins the headers, libraries, corresponding sources and notices, and includes the application object and every actual linker input for relinking. Complete persistent VM-crash/storage-fault evidence remains required.

The current journal is bounded to 32 MiB and rotates automatically before another event exceeds that bound. Four closed generations retain their journal and matching wtmp/btmp/auth projections. Live session starts carry into the new generation as state without duplicating historical login events; their original lease descriptors remain valid. Journal sequences are local to each generation, while auth-log event numbers increase across rotations. Current utmp retains live occupants; expired dead slots remain represented by logout events in the retained history.

Rotation synchronizes an immutable archive and a protected intent record before replacing the current journal. Recovery validates the archive and completes interrupted publication before accepting another event. It reopens the replacement journal and expires older archives only after successful publication. Space for one provisional archive is needed during recovery. Unsafe metadata, corrupt frames, exhausted storage and more than 1,024 simultaneous live leases fail explicitly. Native checks pass 726 cases, including 698 actual injected publication failures or short writes. The unwrapped guest matrix passes 49 boots, including sixteen clean ext2 reboot pairs and a real append/rotation at the default 32 MiB boundary. Independent host decoding verifies archive authority, carried sessions, global event counts, projections, metadata and filesystem checks. These clean reboots do not establish interrupted VM or real storage-failure recovery, which remain required.

## Interactive commands

The development frontend supports these explicit commands and the `login`, `su`, `sudo` and `passwd` aliases:

```sh
account-access provision admin /home/admin /bin/bash
account-access login
account-access su alice -c 'id'
account-access sudo -u root id
account-access passwd
```

The aliases use the same password, identity, terminal and journal policy. `su - NAME` and `su --login NAME` select a login environment; `sudo -u NAME COMMAND...` selects the target identity. They support the options shown here; wider command options remain future account work.

Login verifies the selected account's password. Ordinary su verifies the target's password; a real root caller may select an existing identity. Sudo verifies the caller's password and current `sudo` membership on each invocation, then runs the selected account, including locked root. There is no authentication cache. Ordinary passwd verifies the old password and can update only the caller's account. Private confirmation and minimum-age checks apply to normal changes. Forced changes complete and reauthenticate before a shell can run.

The frontend requires a privileged installation and a foreground controlling terminal. It preserves redirected stdin/stdout/stderr for sudo while supplying a private controlling terminal for separate `/dev/tty` prompts. Inherited environment is cleared before authentication and the command receives its validated profile environment. Only a real root caller can select alternate database/logbook paths. Password updates revalidate the authenticated generation while holding the database lock, audit intent and completion without secret data, and report whether publication happened if a later operation fails.

The new root console supervisor asks for an administrator name only when the protected database is fresh, then delegates private password confirmation to the access frontend. Successful provisioning requires login before a shell starts. Later console starts preserve the existing administrator and require authentication again. Missing committed state blocks authentication and cannot trigger reprovisioning. The supervisor checks the worker's root ownership, single link and exact set-UID mode before password entry, and restores terminal settings and flushes pending input after every worker, including a killed password reader.

`scripts/build_accounts.py` builds accountctl, the access frontend and the console service against each supported provider and linkage. Normal root filesystems install these programs, aliases and conventional account/login-record paths. Init supervises the authenticated console, retires abandoned physical-console workers, restores terminal flags/settings/input and waits a real second before restarting it. The service opens its controlling terminal read/write because init correctly supplies read-only stdin. No failed fork or exec starts a fallback shell. The production policy is private administrator creation on first boot, with persistent state and required login on later boots. A missing, damaged or unavailable committed store blocks authentication.

The [normal VM launch commands](build.md) preserve an ext2 disk outside disposable build outputs. A directly booted RAM-root ISO is a fresh, disposable environment. Reuse the persistent VM disk for subsequent boots with the same account.
