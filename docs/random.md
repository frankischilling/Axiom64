# Kernel randomness

`getrandom`, `/dev/random`, `/dev/urandom`, and ELF `AT_RANDOM` consume one kernel generator. A BLAKE2s-256 pool mixes inputs and derives keys. ChaCha20 generates each 64-byte block with counter and nonce zero: the first 32 bytes replace the old key, and up to 32 bytes from the second half are returned. The unused tail and temporary block/state are erased. Each following block uses the new key, so there is no repeated key/counter pair. Pool extraction also advances its state before retaining it. The current single-CPU kernel serializes these operations with interrupts disabled; adding SMP requires synchronization at this module.

Boot checks CPUID leaf 7, subleaf 0, EBX bit 18 before executing RDSEED. CPU entropy is trusted by default; `random.trust_cpu=off` disables that source. Four successful 64-bit words establish the 256-bit initialization threshold. Each word gets at most ten instruction attempts, and a clear carry flag discards the candidate. Zero, all-ones, duplicate words within a sample, and repetition of the previous sample's final word reject the whole candidate. Failed candidates are erased and retried after 100 ms. A successful initialized source is sampled again after 60 seconds. Failed reseeding preserves the existing generator and retries; it never substitutes a constant seed or an unchecked instruction result. RDRAND alone does not initialize this implementation.

These checks catch some failed or stuck sources; they do not establish or certify physical entropy quality. Crediting RDSEED depends on the CPU or hypervisor implementation and the selected trust policy. Boot counter values and ordinary writes to either device are mixed without credit. If RDSEED is unavailable, fails, or is disabled by policy, initialized output remains unavailable until a supported trusted source succeeds. Persisted seed rotation, other validated sources, and identity-gated seed administration remain tracked in #10. There is currently no userspace mechanism to mark a supplied seed trusted.

## Linux interface behavior

`getrandom` accepts `GRND_NONBLOCK` (1), `GRND_RANDOM` (2), and `GRND_INSECURE` (4). Unknown bits and the combination of `GRND_RANDOM` with `GRND_INSECURE` return `EINVAL`. Flags have Linux's unsigned-int width. Default and `GRND_RANDOM` requests wait for initialization; `GRND_NONBLOCK` returns `EAGAIN` before it. Initialization is checked even for a zero-length request. Explicit `GRND_INSECURE` bypasses that wait and does not establish readiness. Once ready, requests of at most 256 bytes complete without a signal-induced partial result. Larger requests can return a short result of up to 4096 bytes. Invalid destinations return `EFAULT`, or the already-copied count when a later destination chunk fails. Initialization waits are interruptible and honor `SA_RESTART`.

`/dev/random` waits for initialization; `O_NONBLOCK` reads return `EAGAIN` before it. Scalar zero-length device reads also check readiness, after validating the destination address. Empty `readv` requests return zero before device dispatch, matching the Linux VFS contract. Poll reports readable after initialization and writable before initialization. `/dev/urandom` follows Linux's early-output behavior and is readable before initialization; that output has the same limitation as `GRND_INSECURE`. Both devices return up to 256 bytes per read and accept uncredited writes. `RNDGETENTCNT` reports zero before initialization and 256 afterward. Credited-seed and reseed-management ioctls return `EOPNOTSUPP`; unknown ioctls return `ENOTTY`. ELF `AT_RANDOM` uses the same generator, with early uninitialized output permitted so init can bootstrap. Applications requiring initialized output must use default `getrandom` or `getentropy`. The pinned musl `getentropy` implementation retries `EINTR` internally and rejects requests larger than 256 bytes with `EIO`.

## Verification and remaining work

Run `make test-random-native` for RFC ChaCha20/BLAKE2s vectors, every split around hash block boundaries, independent generator outputs, erased contexts, readiness, uncredited mixing, key replacement, carry failures, stuck words, bounded retries, and reseeding under ASAN/UBSAN. Run `make test-random` for twenty actual guest kernels: both musl linkages on BIOS/UEFI, RDSEED enabled, both CPU instructions absent, RDRAND alone, and CPU trust disabled. Initialized cells repeat as new QEMU processes and require distinct samples. Actual child processes check initialization blocking, nonblocking errors, signals, `SA_RESTART`, libc retry, scalar empty reads versus empty `readv`, device polling, copy faults, and shared output across eight forked readers. Each unready kernel checks eight blocked/interrupted/restarted clients, including zero-length random-device reads. Distinct samples are regression evidence against the old repeating stream, not an entropy estimate. Reports and logs use `build/random-*`.

`python3 scripts/manager_reboot_test.py` runs eight pairs of independent kernels using the same ext2 root across both linkages, BIOS/UEFI, and modern/legacy virtio. The first process synchronizes profiles and MAC/address-only hints before SIGKILL. Host inspection checks exact bytes, private metadata, volatile runtime absence, and filesystem consistency. The second kernel starts without prior addresses or runtime records, sends fresh INIT-REBOOT transactions on both adapters, validates the new ACK's prefix and resolver values, probes before installation, and performs checked release/withdrawal. Its transaction IDs must differ from the first boot; the prior fixed-seed implementation failed this assertion. The saved profile must remain unchanged, released hints must disappear, and independent host fsck must pass. Evidence uses `build/manager-persistent-results.json`, phase logs, dumps, and disposable root images.

Saved-state peers advertise 300-second leases with renewal at 150 seconds and rebinding at 262 seconds, beyond their 120-second observer deadline. These fixtures require no renewal/rebinding traffic so synchronization timing cannot change the first boot's accepted tuple before its saved-state assertion. The original protocol fixtures keep their exact 30/8/15-second and changed 100/50/87-second values; the permanent packet replay checks both contracts.

Issue #10 remains open for full seed lifecycle, further entropy-source validation, credentials and privileged administration, and real TLS/key-generation clients. Issue #78 retains its complete packet-loss/malformed/lease/carrier/device-fault matrix and normal-init supervision requirements.

`python3 scripts/random_test.py --reseed --timeout 150` adds two static guest kernels that independently wait through the real 60-second reseed interval, require the checked RDSEED refresh marker, and read initialized output afterward. CI runs these together with the twenty interface cases, for 22 random boots, while the saved-state pairs run separately.

The primitives follow [RFC 8439](https://www.rfc-editor.org/rfc/rfc8439.html) and [RFC 7693](https://www.rfc-editor.org/rfc/rfc7693.html). Instruction semantics follow the [Intel DRNG guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html). Early output, pool writes, fast key erasure, and initialization waits are compared with [Linux v6.12](https://github.com/torvalds/linux/blob/v6.12/drivers/char/random.c); empty read and vector behavior follows the [Linux v6.12 VFS](https://github.com/torvalds/linux/blob/v6.12/fs/read_write.c); libc retry follows [musl v1.2.5](https://git.musl-libc.org/cgit/musl/tree/src/misc/getentropy.c?h=v1.2.5). QEMU 8.2.2 TCG routes RDSEED through its [random instruction helper](https://github.com/qemu/qemu/blob/v8.2.2/target/i386/tcg/int_helper.c), which obtains bytes through `qemu_guest_getrandom`; VM snapshots/clones and hypervisor trust require separate lifecycle work before broader security claims.
